# 别把 AI Agent 直接丢进项目：用 OpenHands 做一个可回滚的小任务

“帮我把这个项目整理好。”这句话听起来很清楚，交给 Agent 却几乎等于没有交代。它可能先改配置，再安装依赖，最后留下几十个你不敢合并的文件。人还没省下时间，审查成本先翻了一倍。

OpenHands 这类开发 Agent 更适合从一个小、可恢复、能验收的任务开始：读取测试目录，定位一个明确报错，提出修复计划，修改指定文件，运行已有检查，再把 diff 和失败项交回来。第一次不要让它碰生产分支、真实密钥和不可逆脚本。

> 安装入口、模型接入、运行环境和权限选项会随版本变化。本文提供任务设计方法和低风险练习，具体命令以当前官方文档和仓库为准。

## 一、先准备一个可以退回去的项目

准备一个公开示例仓库或个人练习项目，完成三件事：新建分支或可恢复副本；删除密钥、客户数据和生产地址；确认项目已有至少一条测试或检查命令。

给 Agent 的范围写成白名单：允许读取哪些目录、允许修改哪些文件、允许运行哪些命令、禁止触碰什么。不要只说“不要乱改”，要写出路径和动作。

## 二、把大目标改成任务卡

| 项目 | 写法示例 |
| --- | --- |
| 目标 | 修复 tests 中一个明确失败的断言 |
| 允许读取 | src、tests、项目说明 |
| 允许修改 | src/parser.py 与对应测试 |
| 禁止动作 | 不改依赖锁文件、不联网、不碰部署配置 |
| 验收 | 原测试与回归测试通过，diff 不超过两个文件 |
| 交付 | 变更摘要、命令输出、未解决问题和回滚方法 |

如果任务写不出验收条件，先别启动 Agent。模糊目标会把“自主”变成“替你猜”。

## 三、第一次只做只读检查

先让它回答：项目入口在哪里？失败点可能在哪？完成任务需要哪些文件？要求它给出路径、理由和不确定项。

可以这样交代：

> 只读取 src/ 和 tests/。先定位测试失败原因，列出准备查看和可能修改的文件，不要写入、不安装依赖、不联网。无法确认时暂停提问。

只读阶段如果已经越界，后面不要继续扩大权限。你要观察的是它有没有遵守范围，而不是它能不能一次猜中答案。

## 四、再允许小范围修改

只读结果可信后，再给最小写权限。要求先给计划，再修改；涉及删除、数据库、依赖升级、部署、权限、外发和真实密钥时，始终停在人工确认前。

“测试通过”不等于“可以直接合并”。还要看修改是否超出任务卡、是否改变无关行为、是否引入新依赖、是否留下未经解释的警告。

## 五、用同一套证据验收

| 检查 | 通过标准 | 失败时先做什么 |
| --- | --- | --- |
| 范围 | 只有白名单文件变化 | 查看 diff，撤销越界修改 |
| 测试 | 原测试和回归测试通过 | 保存完整输出，区分环境与代码 |
| 解释 | 每处改动都有原因 | 要求补充说明 |
| 安全 | 无密钥、无外发、高危脚本 | 清理敏感输出并重跑 |
| 回滚 | 能用 Git 或副本退回 | 保留补丁和原状态 |

保留一条失败样例。它能帮助下次区分“任务没完成”和“验证不足”。

## 六、适合与不适合交给 Agent 的任务

适合：补一个小测试、解释一段错误、整理模块清单、给出重构计划、修复有明确复现步骤的低风险 Bug。

不适合第一次尝试：生产迁移、支付和权限链路、密钥轮换、批量删除、未经审查的依赖升级、直接发布代码，以及需要承担法律、医疗或安全责任的判断。

如果你只是想补一行代码，普通 IDE 助手可能更轻；如果你需要可审查的项目小任务，Agent 才有明显价值。

## 七、把结果留下来

任务结束后保存任务卡、变更 diff、实际命令输出和未解决事项。下次不要复制整段聊天记录，直接复用任务卡并替换路径、目标和验收条件。

真正值得沉淀的不是“Agent 很聪明”，而是团队知道什么任务可以交、交到哪一步必须停、结果用什么证据接回来。先把一个小任务做稳，再考虑更宽的权限和自动化。
