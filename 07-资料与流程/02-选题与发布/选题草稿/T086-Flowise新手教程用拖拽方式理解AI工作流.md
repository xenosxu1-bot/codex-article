# 不想一上来写代码？用 Flowise 看懂一条 AI 工作流怎么跑

很多人第一次接触 AI 工作流，都会遇到一个尴尬：Prompt 会写，工具也知道不少，可一旦问题变成“模型前面接什么、资料从哪里进来、答案怎么出去”，就不知道该从哪里下手。

于是有人直接复制一套复杂 Agent 模板。节点连得很满，运行起来却不知道哪一步在起作用；换一个模型、换一份资料，整条流程又坏了。

Flowise 更适合拿来做一件事：把原本藏在代码里的输入、模型、检索、记忆和输出，摊开成一张可以观察的流程图。第一篇教程不需要做多 Agent，也不需要接十个工具。先搭一条能解释、能运行、能排错的最小工作流，才算真正入门。

## 一、先理解节点，不要先背工具名称

一条 AI 工作流，本质上是在回答五个问题：

1. 用户输入了什么；
2. 哪个模型负责理解和生成；
3. 模型需要参考哪些资料；
4. 是否需要记住前面的对话；
5. 最终结果通过什么方式返回。

在 Flowise 里，这些职责通常会被拆成不同节点。节点不是装饰，也不是越多越高级。每增加一个节点，就增加了一个可能出错、需要配置、需要解释的环节。

新手可以先把节点分成四组：

- **输入**：聊天输入、文本输入或外部请求；
- **模型**：负责理解问题和生成回答的 Chat Model 或 LLM；
- **资料**：文档、检索器、向量数据库和重排组件；
- **输出**：聊天回复、API 返回或嵌入式聊天窗口。

如果一条流程还不能用一句话说明每个节点的作用，就先不要继续加节点。能讲清楚，比能连起来更重要。

## 二、第一条流程只做“问题进来，答案出去”

第一次搭建，建议先做一个不接知识库的聊天流程：

> 用户输入 → 聊天模型 → 文本回答

这个流程看起来简单，却能帮助你确认三件事：模型凭据是否有效，输入是否正确传递，输出是否能够稳定返回。

搭建时不要一开始就追求复杂提示词。先给它一个具体身份和回答边界，例如：

> 你是一个会议纪要整理助手。只根据用户提供的文字提取行动项，不补充原文没有出现的负责人和截止时间。如果信息缺失，明确标记“待确认”。

然后准备三条测试输入：一条正常纪要、一条没有负责人或日期的纪要、一段与会议无关的文字。

你要观察的不是回答是否“聪明”，而是它有没有按边界工作：缺失信息会不会自己补齐，无关问题会不会装作知道，输出格式是否每次都变化很大。

## 三、第二步再加入资料检索，别把知识库当成魔法

当基础聊天流程稳定后，再加入文档问答。一个最小的资料问答流程，通常包含：

> 用户问题 → 检索相关片段 → 聊天模型结合片段回答

这时要特别注意，资料节点和模型节点不是一回事。资料节点负责找到可能相关的内容，模型节点负责组织回答。检索结果找错了，模型再强也只能根据错误上下文继续回答。

准备资料时，先选三到五份同主题、已脱敏的文件。不要把整个电脑里的文档一次性导入。测试资料最好有明确结构，例如产品说明、常见问题和版本记录。

每次提问后，至少检查三件事：

- 检索到的片段是不是在回答同一个问题；
- 片段里的条件和例外有没有被保留；
- 最终回答是否真的使用了这些片段，而不是凭常识补充。

如果资料问答出错，先看检索结果，再看模型提示。不要把所有问题都归咎于模型。

## 四、把“能连上”改成“能解释”

拖拽工具最容易制造一种错觉：线连上了，流程就完成了。实际上，一条可维护的流程至少需要一张节点说明卡。

每个节点写清楚四件事：

| 节点 | 说明内容 |
| --- | --- |
| 输入节点 | 收到什么格式的数据 |
| 模型节点 | 使用哪个模型，负责什么判断 |
| 检索节点 | 从哪里找资料，返回多少内容 |
| 输出节点 | 返回给谁，是否允许直接执行动作 |

当流程出现问题时，按数据流向从前往后排查：输入有没有进入，检索有没有结果，模型有没有读到结果，输出有没有被截断或改变。

不要只保存一张最终画布截图。真正有价值的是：节点名称、凭据名称、提示词版本、测试输入和预期输出都能对应起来。否则过几天你再打开这条流程，仍然要重新猜它是怎么工作的。

## 五、记忆和工具要晚一点加入

聊天记忆很有吸引力，因为它能让对话看起来更连贯。但记忆也会带来新的问题：哪些内容会被保存，保存多久，下一次回答会不会误用上一次的上下文。

工具节点同样如此。让 Agent 可以搜索、调用接口或执行动作之前，先问三个问题：

- 这个工具真的需要吗；
- 它能读什么、写什么或删除什么；
- 执行前是否需要人工确认。

如果只是做资料问答，不需要为了“像 Agent”而加入搜索、代码执行和多个工具。流程越接近真实业务，权限越应该收紧。

特别是可以发送消息、修改记录、公开发布或访问内部系统的节点，不能只用“测试成功”作为上线标准。还要测试错误输入、重复执行和取消操作是否安全。

## 六、不要只测试成功路径，要主动拆坏这条流程

一条流程第一次能回答问题，只能说明它在一个输入上跑通了。正式使用前，至少准备以下测试：

1. 输入为空；
2. 输入过长；
3. 资料库没有相关内容；
4. 两份资料给出不同版本；
5. 模型或外部服务不可用；
6. 用户要求执行超出权限的动作。

每次测试记录四项：输入、发生异常的节点、实际输出、应该怎样处理。

如果检索没有结果，流程应该明确告诉用户“没有找到相关资料”，而不是自动编一个答案；如果模型服务失败，应该返回可理解的错误提示，而不是让用户看到一串内部报错；如果工具动作涉及外部系统，应该有人工确认或可回滚步骤。

Flowise 的可视化界面适合排查数据到底走到了哪一步，但它不能替你制定业务规则，也不能自动保证凭据、访问权限和输出内容安全。

## 七、什么时候用 Assistant、Chatflow，什么时候别急着上 Agentflow

Flowise 官方文档目前将可视化构建方式分为 Assistant、Chatflow 和 Agentflow。对新手来说，不需要把三者一次学完。

可以按需求选择：

- 只想做一个有明确说明和资料问答能力的助手，先从 Assistant 类场景理解；
- 想自己控制输入、模型、检索和输出的连接方式，优先学习 Chatflow；
- 需要分支、循环、多步骤协作或多个 Agent，再考虑 Agentflow。

不要因为 Agentflow 听起来更强，就把第一个练习直接做成多 Agent 项目。复杂度应该由任务决定，而不是由工具菜单决定。

如果你的目标是把表格、消息、邮件和 AI 串成定时运行的业务自动化，n8n 更贴近这个问题；如果你只是想快速做一个可分享的 Bot，扣子更省配置；如果你想理解一条模型、检索和输出链路，Flowise 的画布会更直观。

## 八、今天完成一条能讲明白的 Flowise 流程

今天不要追求“做出一个完整产品”，只完成下面这条最小闭环：

1. 准备三条脱敏测试输入；
2. 搭建输入、模型、输出三个节点；
3. 为每个节点写一句职责说明；
4. 再加入一组同主题资料；
5. 测试一个有答案的问题和一个资料外问题；
6. 记录每个节点的输入、输出和失败表现；
7. 删除不必要的记忆、工具和分支。

验收标准不是“画布看起来很复杂”，而是：

- 你能解释每个节点为什么存在；
- 你知道问题出错时先看哪一个节点；
- 资料外问题不会被包装成确定答案；
- 高风险工具不会无确认直接执行；
- 换一份输入后，流程仍然能按预期工作。

Flowise 最有价值的地方，不是让你少写几行代码，而是让一条 AI 流程从黑盒变成可以观察、可以拆开、可以逐步改进的东西。先把一条小链路看懂，再去做 Agent，速度反而更快。
