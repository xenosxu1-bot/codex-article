# 高完成度首稿创作模板

> 用途：把“热门文章水准”的要求转化为 AI 可以执行、编辑可以复核的首稿合同。
>
> 这份模板只约束创作方向，不规定所有文章必须使用同一种结构。Brief 是后台信息，不能逐项复制到公开正文。

## 1. 使用原则

- 先确定读者此刻遇到的具体问题，再决定文章从哪里开头。
- 先确定一条有立场、可被正文支撑的核心判断，再组织材料。
- 正文允许结构不对称，不要求每个章节长度、句式和小标题数量一致。
- 不把 Brief 写成正文目录，不使用“本文将从……展开”式机械开场。
- AI 可以生成场景和推演，但不得伪造作者亲历、客户案例、生产结果、效率数据、官方背书或未核验产品能力。
- 事实、版权、安全、隐私和链接检查仍按项目现有流程执行；本模板不替代资料核验。

## 2. 首稿 Brief

正式起稿前，在 07-资料与流程/03-资产与核验/文章元数据/NN-中文标题.json 的 brief 中尽量填写：

| 字段 | 要回答的问题 |
| --- | --- |
| target_reader | 谁最需要这篇文章？ |
| reader_moment | 他在什么具体工作时刻遇到了问题？ |
| core_question | 他真正想解决的不是哪个表面问题？ |
| emotional_tension | 他担心失去什么、做错什么或错过什么？ |
| contrarian_claim | 文章要推翻哪种直觉？ |
| new_angle | 与已有文章相比新增了什么价值？ |
| share_target | 读者会转发给谁，转发时想表达什么？ |
| reusable_asset | 读者能带走哪张清单、任务卡、决策树或试验方案？ |
| counterexample | 哪条失败路径或不适用边界必须写出来？ |
| figure_plan | 哪些图分别帮助理解、选择或行动？ |
| not_covering | 明确不写什么，避免文章失焦。 |

## 3. 作者模式提示词

将下面内容与具体 Brief 一起使用：

~~~text
你是一位有技术理解、现场感和编辑判断的中文作者。请根据后台 Brief 创作一篇正式文章初稿。

Brief 只用于内部规划，不要在公开正文中逐项复述，也不要把它机械转换成“背景—定义—优势—步骤—总结”的标准目录。

写作要求：
1. 前 200 字进入一个具体、可感知的工作场景、选择困境或失败路径，不从百科定义开始。
2. 在前 20% 正文内给出一条有立场、可被全文支撑的核心判断。
3. 每个章节都要推进一个新问题：为什么会这样、如何判断、怎样行动、代价是什么、何时不适用。
4. 至少包含一个机制解释、一个反例或失败路径、一个边界条件、一个可在 20～30 分钟内完成的最小试验，以及一个可复用工具。
5. 允许段落长短不一、章节不对称、语气有停顿和转折；不要为了工整而填充重复小节。
6. 删除没有信息增量的套话，例如“本文将”“值得注意的是”“换句话说”“希望本文能够帮助你”。
7. 不编造亲身经历、客户案例、数据、官方背书或未核验能力。没有真实经历时，使用“一个典型场景”“常见情况”或“可以这样推演”。
8. 结尾给出一句适合转发给同事、负责人或朋友的行动型结论，不使用泛泛 CTA。
9. 正文中规划必要的原创信息图，并说明每张图是帮助理解、选择还是行动；封面不嵌入正文，资料链接不放入正文。

输出顺序：
A. 创作骨架：读者冲突、核心判断、章节推进、反例、可复用资产和配图任务。
B. 完整正文。
C. 作者自检：最值得转发的 3 句话、仍显普通的 3 个位置、需进入资料核验台账的事实表述。
~~~

## 4. 正文去模板化要求

初稿完成后，不要立即发布。执行一次独立的总编辑复审：

- 删除重复结论和同义改写。
- 把抽象名词改成具体人物、任务、动作和后果。
- 把小标题改成读者问题、冲突或判断，避免全部使用“是什么、为什么、怎么做”。
- 允许重要章节更长，不强行平均篇幅。
- 保留作者的判断和必要的不确定性，不把一切改成平滑的中性说明。
- 检查每一张图是否真正帮助理解、选择或行动。
- 不添加未经提供的第一人称经历、客户故事、数据或结论。

## 5. 最小验收标准

首稿进入事实核验前，至少满足：

- 有具体读者时刻，不是泛泛“面向所有人”。
- 有一句明确核心判断，不只是主题介绍。
- 有可带走的工具或试验。
- 有反例、代价或不适用边界。
- 有至少一句可以自然转发的判断。
- 正文语气不依赖固定套话，结构不与上一文完全复刻。

质量扫描发现的结构和语气问题只能作为编辑提醒，不替代人工判断，也不自动阻断发布。
