> 一句话结论：搭建 Codex 使用教程，最难的从来不是写出第一篇，而是把入口、路径、来源、素材和更新机制连成一套能长期维护的帮助知识库。

很多人学 Codex，习惯从一条提示词开始：让它改个文件、解释报错、补一段脚本。几次任务做下来，确实会有成就感；可一换项目、一换入口、一换版本，又得重新找资料。

问题不在于教程不够多，而在于教程大多是散的。

我最近把 [Codex_Help](https://github.com/xenosxu1-bot/Codex_Help) 当成了一个很好的样本。它没有把内容做成一份越写越长的大文档，而是拆成中文与英文入口、完整 Markdown 教程、适合浏览的网页导航页、界面素材，以及单独的来源复核说明。读者能从入口开始走，维护者也知道内容从哪里来、改完后要同步什么。

这才是 Codex 值得做的一件事：不只是替你完成一次代码任务，而是帮你搭一套让人持续用得上的使用帮助系统。

## 一、先别急着写教程，先设计读者的下一步

一份帮助知识库最容易犯的错误，是作者知道怎么找，读者不知道下一步点哪里。

新手打开页面，通常只有五个问题：

- 我应该从哪个入口开始：桌面端、命令行，还是 IDE
- 第一件可以照着做的小事是什么
- 遇到配置、权限或运行问题该去哪里查
- 想进阶时，哪些能力值得继续学
- 文档更新后，旧结论还能不能信

因此，内容不该只按写作顺序排，而要按读者完成任务的顺序排。

Codex_Help 的做法值得借鉴：把快速上手、使用入口、界面功能、工作流、配置与扩展能力拆开，再让网页目录承担跳转。读者不必先理解所有名词，先完成一个任务，再回到对应章节补知识就够了。

![教程不是文章堆，而是一条读者路线](<../08-素材库/图片/正文插图/16-Codex_Help-reader-path-v3.png>)

这张路线图背后有一个很朴素的原则：**每一篇教程都要回答“读完以后做什么”。**

比如快速开始的结尾，不是再丢一串概念，而是引导读者选择自己的工作入口；配置篇的结尾，不是把所有参数罗列完，而是告诉读者遇到权限、规则或工具连接问题该回查哪一节。这样，知识库才会从文章集合变成学习路径。

## 二、把前台入口和后台维护分开

读者需要的是清楚，维护者需要的是可追溯。这是两套完全不同的需求。

前台只保留真正影响阅读体验的东西：首页、分类、章节目录、搜索入口、关键截图和下一步链接。Codex_Help 把中文完整教程同时提供 Markdown 与网页导航版，网页端有侧边目录；这一步很小，却直接解决了长教程最常见的问题：读到一半找不到刚才那一节。

后台则要记录另一类信息：

- 这条结论对应哪份官方资料
- 哪些页面和图片需要跟随正文更新
- 哪些章节只是草稿，哪些已经复核
- 页面生成脚本、素材目录和源文件之间有什么关系

当这两层混在一起，读者会看到一堆维护说明；维护者又会漏掉更新动作。把它们分开，才能既方便读，也方便改。

对个人知识库来说，这意味着不必一开始就上复杂系统。一个清晰的目录加一份更新清单，已经足够让 Codex 接手不少重复工作。

## 三、教程的可信度，不靠写得像官方

工具类教程有一个隐蔽风险：产品变化很快，旧教程写得再流畅，也可能把过期操作讲得很肯定。

Codex_Help 把来源复核单独写进 `docs/source-check.md`，并明确自己是学习辅助材料，不替代官方文档。这个边界非常重要。

真正可维护的教程，至少应当做到三件事：

**第一，结论回到原始来源。** 版本能力、权限范围、模型选择、价格和可用性，不要只引用二手经验。能链接到官方说明的地方，就不要用记忆代替。

**第二，把时间敏感内容标出来。** 例如某个入口名称、预览能力、账号权限或模型选项，应该写清复核日期与适用范围，不要假装它永远不变。

**第三，给读者留一条核验路径。** 当页面更新、截图变化或操作不一致时，读者知道该去官方页面确认，而不是把一篇旧文章当成唯一答案。

这不是降低教程的价值，恰恰相反。敢把边界说清楚，读者才敢把它当作日常工作里的参考资料。

## 四、让 Codex 参与的，不该只有正文

如果只把任务交代成“写一篇 Codex 教程”，得到的通常是一篇能读的文章。

如果把任务交代成“搭建一套帮助知识库”，Codex 才会开始同时处理结构、链接、页面、素材和检查。

一张可执行的任务卡可以这样写：

> 目标：新增一个面向新手的 Codex 使用帮助知识库。
>
> 范围：提供快速开始、入口选择、核心工作流、常见问题与官方资料入口；中文为主，保留英文扩展空间。
>
> 交付：Markdown 源文、可浏览的导航页、截图与图片目录、来源复核记录、更新说明。
>
> 验收：每个入口可打开；目录跳转正常；图片路径有效；时效性结论有来源和复核边界；发布前保留人工确认。

这份任务卡的关键不在文案，而在验收。

Codex 很擅长把有明确边界的工作拆成文件、目录和检查动作：生成页面、补目录、检查链接、统一图片命名、找出未引用素材、比较更新前后的改动。人负责判断什么值得写、结论是否成立、是否应该发布；Codex 负责把这些要求落实成可复查的交付物。

## 五、知识库要形成闭环，不能只完成第一次上线

第一次把教程放上去，只是起点。真正拉开差距的是后面能不能持续更新。

以 Codex_Help 的结构为例，正文、网页页、截图素材和生成脚本之间是有关联的：改了教程目录，网页导航要跟着更新；补了界面说明，图片资源要能对应；刷新资料后，来源复核页也要留下痕迹。

![让教程持续可用的五个维护动作](<../08-素材库/图片/正文插图/16-Codex_Help-maintenance-loop-v3.png>)

这套闭环可以压缩成五个动作：

1. 核对来源：先确认官方资料和版本边界，再改结论。
2. 写入教程：把功能翻译成任务场景、步骤和提示，不做资料搬运。
3. 生成导航：让长文、专题页和目录保持一致，保证读者能找到内容。
4. 补齐素材：截图、信息图和说明各自服务一个理解目标，不堆装饰图。
5. 复核更新：检查链接、图片、排版和发布状态，把旧内容留在可追溯范围内。

其中最容易被忽略的是第 5 步。很多教程的问题不是没写好，而是改完正文后忘了更新目录、网页页或图片引用。把复核固定成动作，后面的维护成本会小很多。

## 六、一个普通人也能开始的 7 天版本

不必等到资料很全才开始。先做一个最小版本，反而更容易跑通。

- 第 1 天：写清读者是谁、最常见的三个任务是什么。
- 第 2 天：画出目录，只保留快速开始、入口选择、工作流、常见问题四块。
- 第 3 天：完成第一篇快速开始，用一个真实任务贯穿全文。
- 第 4 天：补一张入口选择图和一张工作流图，让读者先看懂骨架。
- 第 5 天：把长文转换成有目录的网页阅读页，验证跳转与移动端阅读。
- 第 6 天：建立来源复核表和更新清单，记录哪些内容需要定期回看。
- 第 7 天：让一位没有参与搭建的人从首页开始走一遍，记录他卡住的位置。

最后这一步很重要。知识库不是写给自己看的。只要别人第一次使用时还会迷路，目录和描述就还可以继续改。

## 七、最后：把一次提问，变成一项长期资产

Codex 的价值，不只是帮你把代码写得更快。

当你开始用它整理教程结构、维护页面导航、检查素材引用、追踪来源变化时，你会发现它更像一个能执行规则的协作工具。它不替你决定方向，却能把已经决定的方向变成稳定的文件、流程和交付。

如果你正想系统学习 Codex，不妨先从搭一个小型帮助知识库开始。拿 [Codex_Help](https://github.com/xenosxu1-bot/Codex_Help) 的目录做参考，不必照搬内容；先为自己最常用的三类任务写出入口和路径，再让 Codex 帮你把它维护下去。

你最终得到的，不是一份会过期的教程，而是一套会随着使用不断变好的工作说明。
