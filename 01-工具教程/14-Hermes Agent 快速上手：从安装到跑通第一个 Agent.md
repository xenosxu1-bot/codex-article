> 一句话结论：第一次使用 Hermes Agent，不要急着接消息平台、Skills 或 MCP。先在一个非敏感目录里完成安装、选好模型、做一次只读任务、退出后再恢复会话；这四步连起来，才算真正跑通第一个 Agent。

你刚把 Hermes 装好，准备让它先看看一个测试目录。界面能启动、模型也填好了，但眼前同时出现模型、工具、Gateway、Skills 和外部连接。它们都能做很多事，也都可能成为报错来源。

第一天不必把能力一次配齐。先验证一条最短路径：我知道它从哪里启动、它在用哪个模型、它只在什么范围内工作、下一次还能不能接着这个任务继续。

## 先决定：这次只跑一个受控闭环

把第一次使用拆成四个可检查的结果。

1. 固定入口。 在同一个终端或桌面入口完成操作，不在 PowerShell、Git Bash、WSL 和多个安装方式之间来回切换。
2. 固定模型。 用 `hermes model` 明确选定 Provider 和模型，再让它完成一次正常回复。
3. 固定范围。 只对一个测试目录做只读任务，不给它客户资料、密钥、生产配置或私人文件。
4. 固定恢复方式。 退出后用 `hermes --continue` 回到刚才的上下文，确认它没有把范围和结论丢掉。

这比“它能不能马上帮我自动化”更重要。前四项没跑通时，继续配置 Gateway 或外部工具，只会把问题从一个变成四个。

## 安装后先做两件事，不要先接工具

Windows 或 macOS 用户先按官方当前安装页选择对应入口。官方快速入门把桌面端和命令行都列为起点；具体命令、系统支持和下载方式会更新，所以安装当天以官方页面为准，不要从旧教程复制远程安装脚本。

进入 Hermes 后，先按这个顺序操作：

> **第一轮配置卡**
>
> 1. 运行 `hermes setup`，完成第一次配置向导。
> 2. 运行 `hermes model`，只选择一个准备使用的 Provider 和模型。
> 3. 输入一个普通问题，确认它确实有正常回复。
> 4. 运行 `hermes doctor`，把环境或配置问题留在这里解决。

模型选择不是可跳过的装饰项。第一次只保留一个可用模型，能让后续的失败信息更容易判断：是配置、认证、网络，还是任务本身出了问题。回复异常时，先回到 `hermes doctor`、`hermes model` 和 `hermes setup` 逐项核对；每改一项，都重新验证普通对话。

## 给它第一项任务时，把“会做什么”说清楚

第一次任务不建议从“帮我自动化工作”开始。挑一个新建的测试目录，放一份 README 或几个普通文本文件，让它只读取，不修改。

可以直接使用下面这张任务卡：

> **第一个 Agent 任务：项目摸底，只读版**
>
> 请只读取当前目录，不要修改文件，不要安装依赖，也不要执行会改变环境的命令。
>
> 1. 用不超过 5 条说明这里可能是什么项目。
> 2. 找出最可能的启动入口、检查命令或配置文件。
> 3. 每个结论后写出对应的文件名。
> 4. 不能确认的内容明确标为推断。
> 5. 最后给出下一步应由人确认的 3 件事。

这里的重点不是测试它有没有“像人一样理解项目”，而是检查三件小事：它提到的文件是否真的存在；结论能否回到文件里核对；未知项有没有老实写成推断。

提示词里的“不要修改”不能替代工具和权限的约束。第一次任务不接浏览器、消息平台、定时任务或写入工具，是为了把变量减到最少。等只读任务能稳定复核，再逐步扩大范围。

## 别跳过会话恢复，它决定这是不是一条可用路径

很多人第一次跑通对话后就关闭窗口。第二天再打开，往往又从头解释目录、模型和任务边界。对 Agent 来说，恢复能力本身就是使用体验的一部分。

完成只读任务后，先正常退出，再运行 `hermes --continue`。恢复后不要立刻下新任务，而是先问它两件事：刚才的任务范围是什么；哪些结论来自哪些文件。

如果它不能准确复述，不要把这次结果带进更复杂的自动化。先缩小任务，再检查模型和会话配置。第一次的成功标准不是“输出看起来很完整”，而是**下一次能接着核对**。

## Hermes、Codex、WorkBuddy：不是谁更强，而是谁先接住你的工作

这三个产品都可能被称为 Agent，但使用时的感受并不一样。差异首先来自你从哪里开始，而不是聊天框长得像不像。

### Hermes Agent：从能力边界和运行环境开始

Hermes 的第一步是安装、模型选择、工具配置和运行环境。它的好处是路径清楚：你能把模型、工具和外部连接逐步接进来；代价是第一次使用需要愿意处理终端、配置和权限范围。

它更适合两类人：一类是希望把本地目录、命令行、模型 Provider 或外部服务连成自动化流程的开发者；另一类是愿意自己维护环境、想把 Agent 当作个人技术工作台的高级用户。对这类人来说，使用体验的核心是“控制感”和“可扩展性”。

### Codex：从代码库和交付任务开始

Codex 的工作入口更接近软件工程：先给出仓库、任务和验收目标，再让 Agent 在代码上下文中分析、修改、运行检查或协同处理任务。你更常关注的是改了哪些文件、测试是否通过、变更是否符合项目约束，而不是先挑选哪些底层工具。

它更适合已经有代码库的开发者、技术负责人、产品工程师和需要参与代码交付的设计人员。对这类人来说，使用体验的核心是“把任务推进到可审阅的改动”，而不是搭一套通用 Agent 运行环境。

### WorkBuddy：从办公任务和交付物开始

WorkBuddy 的入口更靠近办公任务本身：用自然语言发起任务，再围绕任务补充上下文、上传文件、查看结果和继续追问。它把文档、表格、演示文稿、数据分析、本地文件处理，以及助理、技能和连接器放在同一个工作台里；使用者更常关心结果是否可查看、可继续处理并进入现有办公流程，而不是先研究命令行和模型路由。

它更适合内容与运营人员、项目协作人员、需要处理文档或数据的业务岗位，以及要审核交付物的负责人。对这类人来说，使用体验的核心是从一个明确的办公任务开始；涉及本地文件、连接器或对外发布时，仍要由负责人确认数据范围、权限和最终动作。

### 选工具时，先看你当天要交付什么

- 你要把代码库里的问题改完并跑检查：优先从 Codex 开始。
- 你要把模型、终端、文件和外部服务逐步连成自己的工作流：优先从 Hermes 开始。
- 你要围绕文档、数据、协作或本地文件处理完成一个办公交付：优先评估 WorkBuddy。
- 你暂时只想试试 Agent：不要同时安装三套。 先选和当天任务最接近的一套，跑完一个受控闭环，再决定要不要扩展。

这不是性能排名，也不是同条件实测结论。它只是按三种官方产品入口来划分：代码交付、可配置的 Agent 运行环境，以及办公任务交付。入口选对了，第一天的阻力会小很多。

## 第一天结束前，留下这四条记录

完成第一次使用后，用几分钟写下：使用的入口；当前 Provider 与模型；测试目录；能够恢复的会话或复现步骤。以后接 Gateway、Skills、MCP 或更高权限工具时，这四条记录就是排错的起点。

如果当前还做不到恢复会话或解释任务依据，不要继续加功能。回到只读任务，把模型、范围和诊断走通。能稳定复核的一次小任务，比一套看起来很全但无法定位问题的 Agent 配置更有价值。
