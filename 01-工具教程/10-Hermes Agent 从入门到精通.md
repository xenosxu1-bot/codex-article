# Hermes Agent 实战入门：从最小闭环到安全自动化

![Hermes Agent 任务闭环](<../08-素材库/图片/正文插图/10-Hermes Agent 从入门到精通-正文插图01.png>)

Hermes Agent 是 Nous Research 开源的终端型 AI Agent。它的价值不只是聊天，而是把模型、终端、文件、Skill、消息入口和自动化任务放进同一条可执行链路里。

真正值得学习的不是某个命令，而是怎样把一个模糊目标变成一项有边界、有证据、能复盘的工作。

## 先说清楚：本文验证到什么程度

本文按 **2026 年 8 月 6 日**能查到的官方文档整理安装、配置、Slash Commands、Skills、Cron、委派和安全边界。Hermes 的命令、模型后端和第三方集成会随版本变化，动手前先运行：

~~~bash
hermes --version
hermes --help
hermes doctor
~~~

本文没有在当前文章仓库中实际启动 Hermes，也没有把本地安装、模型连通、消息网关或生产自动化写成已验证事实。下面的实战部分是一套可复现的验收流程，执行结果以你自己的终端输出为准。

## Hermes Agent 到底解决什么问题

普通聊天通常停在回答层：你问一个问题，模型给出一段文字。

Agent 工作流要再往前走一步：

1. 读取任务输入和约束。
2. 调用模型、终端或外部工具执行动作。
3. 输出文件、命令结果、变更记录或报告。
4. 让人能够检查结果，并决定是否继续扩大权限。

因此，Hermes 的核心不是让 AI 变得更会说，而是让 AI 参与一项真实工作时，过程能被观察，结果能被验收，权限能被收回。

## 第一阶段：安装，但不要急着全开

### 1. 选择安装环境

Linux、macOS 和 WSL2 通常更适合终端型 Agent。Windows 原生环境也可以使用，但要提前确认 PowerShell、Python、Node.js、Git、ffmpeg 和 ripgrep 等依赖是否可用。

如果你准备让 Agent 读写项目文件，建议先建立一个专用工作目录，不要直接把整个用户目录作为工作根目录。

### 2. 使用官方安装入口

官方文档提供脚本安装方式。脚本本身会改变本机环境，执行前先阅读内容，确认来源、目标路径和依赖，再决定是否运行。

~~~bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
~~~

~~~powershell
iex (irm https://hermes-agent.nousresearch.com/install.ps1)
~~~

更稳妥的做法是固定一个已知版本，记录安装日期和版本号，并保留回滚方式。不要把一条未经审阅的远程脚本当成无风险命令。

### 3. 完成最小诊断

~~~bash
hermes --version
hermes doctor
~~~

至少确认四件事：

- 命令能被系统找到。
- Python 和终端依赖没有明显错误。
- 模型或 Portal 配置已经被识别。
- 当前工作目录和权限范围符合预期。

## 第二阶段：完成一个可核查的只读任务

第一次任务不要让 Agent 改代码、发消息、删除文件或访问生产凭据。先做一个只读任务，目标是验证完整闭环。

把下面这段任务提示词放进 Hermes 的会话中：

~~~text
请在当前项目目录执行一次只读检查，不修改任何文件，不联网，不发送消息。

目标：
1. 列出项目根目录下的一级目录和文件类型分布。
2. 找出最近修改的 10 个文本文件。
3. 识别可能存在的 README、AGENTS.md、package.json、pyproject.toml 或类似项目说明文件。
4. 输出一份 Markdown 检查报告，报告只写入临时目录，不覆盖项目文件。

要求：
- 每一步都说明使用了什么命令。
- 记录命令的退出状态。
- 如果无法完成，说明失败原因，不要猜测。
- 最后给出下一步建议，但不要自动执行建议。
~~~

这段任务故意设置了四个边界：只读、限定目录、输出可验收、失败不猜测。它比让 Agent 一上来写一整个功能更适合发现环境问题。

### 任务验收清单

执行完后检查：

- 是否真的没有修改项目文件。
- 报告是否包含命令、结果和失败信息。
- 报告中的文件数量能否在终端重新核对。
- Agent 是否把不存在的配置、路径或测试结果写成了事实。
- 终端历史、日志或输出文件中是否泄露了 Token、Cookie 和本地隐私路径。

## 第三阶段：把一次任务变成可复用流程

当只读任务稳定后，再按下面的三轮方式推进。

### 第一轮：只读观察

目标是获得事实，不改变环境。

- 读取项目说明和目录结构。
- 运行状态检查和测试命令。
- 输出问题清单和证据位置。
- 不自动修复，不扩大权限。

### 第二轮：小范围写入

只开放一个临时目录或一个明确文件，并要求 Agent 先给出变更计划，再执行。

- 先列出拟修改文件。
- 先说明修改原因和回滚方法。
- 执行后输出 diff 或变更摘要。
- 运行针对性检查。
- 由人确认后再合并。

### 第三轮：沉淀为 Skill

当同一类任务重复出现，才把稳定做法写成 Skill。一个合格的 Skill 至少要说明：触发条件、输入、输出、工具边界、失败恢复、验收标准和禁止事项。

不要把一次偶然成功的提示词直接升级成永久规则。先积累多次真实结果，再区分哪些是稳定经验，哪些只是某次环境的巧合。

## 命令、Slash Commands 和 Skill 不要混为一谈

Hermes 中有三类不同入口：

| 类型 | 例子 | 作用 |
| --- | --- | --- |
| Slash Commands | /new、/reset、/retry、/undo、/compress | 控制当前会话状态或上下文 |
| CLI 命令 | hermes --version、hermes model、hermes doctor | 在终端中检查或配置 Hermes |
| Skill | 项目内的技能目录和说明文件 | 把一类重复任务的做法沉淀为可复用能力 |

不要把 /reset 当成重新安装，也不要把一个 CLI 命令写成模型能力。遇到版本差异时，优先用 hermes --help 和当前版本文档确认。

## Skills 和记忆：让 Agent 变好，而不是变死

Skill 适合保存稳定流程，例如：

- 如何运行一组固定检查。
- 如何生成统一格式的报告。
- 如何在指定目录内处理素材。
- 如何在写入前生成 diff 并执行验证。

记忆适合保存经过多次验证的偏好和上下文，例如项目目录、命名习惯、常见失败原因和已确认的工作边界。

以下内容不要直接写入长期记忆：

- 未验证的猜测。
- 临时 Token、Cookie、密码和私钥。
- 只发生过一次的偶然经验。
- 与当前项目无关的个人隐私。
- 没有时间和版本边界的易变事实。

有效的复盘记录应该包含四项：问题、证据、修复、预防。下次遇到同类任务时，先检索历史失败记录，再决定是否复用规则。

## 第四阶段：网关、Cron 和委派

这些功能带来的不是单纯的效率提升，而是更大的权限和运行风险，所以应在前面三轮稳定后再打开。

### 消息网关

Telegram、Discord、Slack、WhatsApp、Signal 等入口会让 Agent 从主动工具变成持续接收消息的服务。至少要先配置：

1. 明确允许交互的账号或群组。
2. 区分只读命令和写入命令。
3. 限制可用工具和工作目录。
4. 对外发消息设置人工确认。
5. 保存审计日志，但过滤敏感信息。

### Cron

Cron 适合定时检查、生成报告或提醒，但每次任务可能在新的会话中执行，因此提示词必须自包含：明确目录、输入、输出、时区、失败处理和权限边界。

一个合格的 Cron 任务至少写清楚：

- 什么时候运行。
- 读取哪些文件或数据。
- 结果写到哪里。
- 失败后只记录还是重试。
- 是否允许联网、写入、发消息。
- 谁负责查看结果。

不要使用只在当前对话里成立的上下文，例如要求 Agent 继续一个已经结束的对话。定时任务必须能够在新会话中独立理解。

### 子 Agent 委派

委派适合把相互独立的工作拆开，例如一个 Agent 做只读扫描，另一个 Agent 负责整理报告。委派时必须写明目标、输入、输出、工作目录和禁止操作。

父 Agent 不应默认相信子 Agent 的结论。子任务的结果仍要回到主流程，经过证据检查和人工确认。

### 后端和沙箱

根据官方文档，当前后端选择包括 local、Docker、SSH、Singularity、Modal 和 Daytona。具体可用项会随版本、地区和账户配置变化，不能把某个后端名称写成所有环境都能直接使用。

如果任务涉及不可信代码、批量写入或外部网络，优先考虑隔离环境，并先用最小权限验证，再逐步扩大范围。

## 安全配置的最低要求

在打开自动化前，逐项确认：

- 默认工作根目录不是整个用户目录。
- 写入目录是显式指定的。
- 删除、覆盖、发送消息和外部发布需要确认。
- .env、SSH 密钥、浏览器 Cookie 和 Token 不会进入提示词或报告。
- 网关账号使用 allowlist，不接受任意用户指令。
- Cron 任务有超时、失败处理和审计记录。
- 子 Agent 只能访问完成任务所需的上下文。
- 不可信代码在 Docker、Singularity 或其他隔离环境中执行。
- 每次升级后重新运行诊断和最小只读任务。
- 发生异常时能够停用网关、撤销凭据并回滚文件。

安全不是最后补一段提醒，而是写进任务提示词、目录权限、工具配置和验收清单。

## 四周学习路线

### 第 1 周：会用

完成安装、模型配置、版本诊断和一次只读任务。目标是知道 Hermes 能访问什么，不能访问什么。

### 第 2 周：会交付

让 Agent 完成一个小范围、可回滚的任务，例如整理 Markdown、生成检查报告或补充测试说明。每次都要求输出变更摘要和验证结果。

### 第 3 周：会复用

把重复出现的做法沉淀为 Skill，给 Skill 增加输入格式、失败恢复和验收标准。删除没有证据支撑的规则。

### 第 4 周：会自动化

选择一个低风险、可观察、可停止的 Cron 任务。先运行几次观察稳定性，再考虑消息网关、委派和更复杂的后端。

## 最终验收标准

当你能回答下面六个问题，才算完成入门：

1. Hermes 当前版本是什么？
2. 当前会话和定时任务分别能访问什么？
3. 哪些操作是只读，哪些操作需要确认？
4. 一次任务的证据保存在哪里？
5. 失败时如何停止、回滚和复盘？
6. 哪些经验已经验证到足以沉淀为 Skill？

官方安装、Windows 原生、Slash Commands、Skills、Cron、委派、配置和安全边界，应以 Hermes 官方文档的当前版本说明为准：https://hermes-agent.nousresearch.com/docs/。本文提供的是一条从最小闭环开始的实践路线，不替代你的本地安装验证、权限审查或生产发布审批。
