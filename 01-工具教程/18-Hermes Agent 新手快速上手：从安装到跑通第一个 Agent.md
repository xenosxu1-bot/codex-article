> 一句话结论：第一天只验证 Hermes 能启动、模型能回复、只读任务可复核、会话能续接；Gateway、Skills 和 MCP 留到基础链路稳定之后。

第一次安装 Agent，最容易发生的不是“装不上”，而是一次配置太多：模型、工具、Gateway、Skills、MCP 同时上，最后不知道哪一步真正带来了问题。

新手的第一天不需要做出一个全能助手，只需要跑通一条能解释、能复核、能继续的最小闭环。

下面这条 30 分钟路线，把成功标准从“终端没有报错”改成“我知道它刚刚做了什么，也知道下一步怎么继续”。

## 一、今天是否成功，只看 4 个验证点

Agent 不只是能对话的窗口。它还会在明确的运行环境里调用模型、读取上下文、使用工具，并把过程变成可以继续和核对的工作。

所以第一天的验收不要看功能数量，只看下面四件事是否成立：

1. 输入 `hermes` 后，命令能在同一套终端环境中启动。
2. 完成模型配置后，能得到一次正常回复。
3. 它能完成一项只读目录任务，并把结论和文件证据对应起来。
4. 结束后能找到并续接刚才的会话，而不是从头再讲一遍上下文。

四项都通过，才算基础闭环跑通。

其中任何一项没通过，都不是失败，而是一条可以定位的信号：启动问题先看环境，回复问题先看模型，只读任务问题先核对权限和文件证据，会话问题再回到入口和上下文。一次只处理一个信号，排查才不会失控。

## 二、前 10 分钟：只把环境与模型跑通

先按当前系统和 [Hermes Agent Quickstart](https://hermes-agent.nousresearch.com/docs/getting-started/quickstart)、[Installation](https://hermes-agent.nousresearch.com/docs/getting-started/installation) 选择安装方式。Windows 用户尤其要避免在 PowerShell、Git Bash 与 WSL 之间来回切换：安装、配置和第一次运行尽量放在同一套终端环境里。

安装完成后，只做两件事：

> - 启动命令：`hermes`
> - 模型配置命令：`hermes model`

此时不要急着增加 Skills 或连接其他服务。先记录你配置的是哪个模型提供方、当前会话在哪个终端运行；以后出现问题，这两条信息最先帮助你缩小范围。

如果启动或模型配置不稳定，先按这个顺序处理：`hermes doctor` → `hermes model` → `hermes setup`。每做完一步再重新启动一次，不要把多轮修改混在一起。

## 三、中间 10 分钟：只做一个可复核的只读任务

第一次任务最适合选当前目录，但权限要收紧到“读取和说明”。提示词不能替代系统权限，不过它能把你希望看到的交付格式说清楚。

> **第一次任务卡**
>
> 请先只读当前目录，不要修改任何文件，也不要执行会改变环境的命令。
>
> 1. 判断这可能是什么项目。
> 2. 找出最可能的启动入口。
> 3. 找出测试、构建或检查命令。
> 4. 每个结论后标明它来自哪个文件；无法确认的内容明确写为推断。
> 5. 最后给我一份不超过 8 条的新手上手清单。

这张任务卡就是第一条案例证据：你不必相信“它看起来很聪明”，只要检查它列出的文件是否存在、结论是否能回到文件中核对、未知部分有没有被明确标为推断。

## 四、最后 10 分钟：验证会话能不能接上

一次任务做完并不等于能持续工作。把刚才的任务留在同一会话里，再验证一次续接。

> - 续接会话：`hermes --continue`
> - 列出会话：`hermes sessions list`

续接后，可以继续给出这句要求：

> 基于刚才找到的 README 和配置文件，把上手清单改成一个 30 分钟执行计划。保留文件证据，不确定的地方不要补写。

如果它能延续刚才的文件证据和限制条件，你就完成了“状态可续接”的验证；如果不能，先检查是否在同一终端环境、同一账户与同一会话入口中操作。

这一步的合格标准不是它把计划写得多漂亮，而是你能看见两件事：它引用的是刚才确实读过的文件，它保留了“只读”“不确定不补写”这类限制。若这两点丢失，就把问题记为“会话或上下文续接未确认”，不要用继续增加配置来掩盖它。

*图 2：把 30 分钟拆成可检查的节点。*

## 五、Hermes 和 Codex：先按工作台分工

Hermes 与 Codex 不需要先争“谁更强”。更实用的判断是：你现在需要的是哪一种工作台，以及哪一段结果需要交接。

- 当你要把一个本地目录、运行环境和持续会话串成可复核的 Agent 任务时，可以先用 Hermes 完成只读探索与会话续接。
- 当你要在代码仓库里推进实现、检查改动、运行项目验证时，再按团队既有的 Codex 工作流执行。
- 无论交给哪个工具，任务边界、可执行命令、可修改范围和验收方式都要写清楚。

产品能力与安装方式会更新；需要配置时，分别以 [OpenAI Codex 官方仓库](https://github.com/openai/codex) 和 Hermes 的当前 Quickstart 为准。

## 六、这 3 件事，先留到第二轮

基础闭环还不稳定时，先不要急着扩展：

1. **Gateway：** 先确认启动、模型和只读任务稳定，再处理外部连接与服务暴露。
2. **Skills：** 先用一条任务卡证明基础能力，再为重复工作加专门能力。
3. **MCP：** 先明确它会接触哪些数据、需要什么权限、失败时怎样停下来和回退。

把复杂度往后放，不是放弃能力，而是让每一次新增配置都有独立的验证结果。

## 七、今天可以带走的最小行动清单

> - 在一套固定终端里启动 Hermes；
> - 用 `hermes model` 跑通一次模型回复；
> - 用只读任务卡检查一个目录，并核对文件证据；
> - 用 `hermes --continue` 验证会话续接；
> - 把 Gateway、Skills、MCP 写在第二轮清单里，而不是现在一起安装。

完成这五步后，再根据你真正重复出现的工作，决定下一项要增加什么能力。第一天的目标不是“把所有功能打开”，而是建立一条你能解释、能复核、也能继续的 Agent 工作路径。
