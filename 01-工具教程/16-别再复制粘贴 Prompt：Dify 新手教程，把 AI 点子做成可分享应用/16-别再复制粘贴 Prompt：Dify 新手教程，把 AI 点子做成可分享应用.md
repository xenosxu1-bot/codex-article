**16. 别再复制粘贴 Prompt：Dify 新手教程，把 AI 点子做成可分享应用**

你可能也有过这种经历：和 AI 聊了半小时，终于调出一段满意的 Prompt；第二天想再用，却要重新翻聊天记录，换个人更不知道该怎么填。Prompt 本身没有消失，真正消失的是使用边界和稳定流程。

第 14 篇，我们搭了一个本地 AI 助手；第 15 篇，我们把资料整理成可以追问的知识库。今天再往前走一步：把一段只存在聊天记录里的 Prompt，做成一个别人也能填写、测试和分享的小应用。

这篇仍然不做“万能 AI 平台”导览，只带你完成一个低风险的周末出行小助手。看完后，你应该有一个能填写变量、执行测试、写清使用边界的最小应用。

> 资料核验时间：2026-08-11。Dify 的产品定位、云端与自托管方式、Docker Compose 部署、模型配置和知识库/工作流边界，以 Dify 官方文档、官方 GitHub 仓库和许可证说明为准。本文配图为本仓库原创信息图，不使用官方 Logo、官网截图或第三方博客图片。

## 一、从复制 Prompt 到一个小应用

Dify 不是一个“更漂亮的聊天框”。它更像一个把模型、提示词、变量、知识库、工作流和发布入口组合起来的应用开发平台。

聊天时，你只是在临时发消息；做成应用后，你要提前决定用户填写什么、模型负责什么、输出长什么样，以及哪些事情不能承诺。所以第一版不需要追求复杂，只要让一个小应用稳定完成一个动作，就比收藏一堆没有边界的 Prompt 更有价值。

## 二、先做窄场景，再选择云端或本地

不要一上来做“万能生活助手”。先选一个能在周末完成、能由自己验收的窄问题，例如：根据城市、日期、预算、同行人和限制条件，生成半天或一天的低压力出行草案。

这个场景有明确输入，也容易发现错误。你可以检查它有没有忽略预算、有没有把不确定的天气和营业状态说成事实、有没有考虑老人或孩子的体力。第一版先排除高风险承诺：不要让它保证一定有票、一定不排队、一定准时，也不要让它替代医疗、法律、财务等专业判断。

Dify 可以使用云端服务，也可以按官方文档进行自托管部署。选择前先回答三个问题：谁会使用、资料是否敏感、你是否愿意维护服务器和升级。

| 你的情况 | 推荐路线 | 需要提前想清楚 |
| --- | --- | --- |
| 只是验证一个点子 | 先用云端体验 | 账号、额度、数据边界和分享权限 |
| 已经熟悉 Docker | 评估本地自托管 | Docker Compose、数据卷、升级和备份 |
| 要给多人持续使用 | 先做权限和运维设计 | 用户、日志、版本、密钥和故障恢复 |

本地部署不是“下载后就不用管了”。官方 Docker Compose 方案涉及镜像、端口、环境变量、数据库和持久化目录。无论选哪条路线，都不要把 API Key、组织 ID、内部地址或真实用户资料写进文章、截图和公开仓库。

## 三、把需求拆成变量

打开应用编辑界面后，先不要急着写一大段 Prompt。把每次都会变化的信息拆成变量，让使用者知道应该填写什么。

| 变量 | 用户填写示例 | 用途 |
| --- | --- | --- |
| city | 杭州 | 限定城市范围 |
| date | 本周六 | 提醒用户核对天气、营业时间和交通 |
| budget | 人均 200 元 | 控制建议档次 |
| people | 两个大人一个小学孩子 | 决定节奏和体力强度 |
| constraints | 不想排队太久，孩子晕车 | 排除不适合安排 |

变量不要太多。第一版 3 到 6 个就够了。每多一个输入，使用者就多一分放弃的可能。能由应用自动处理的固定信息，不要让用户重复填写。

## 四、写系统提示词并完成第一次运行

应用提示词不要只写“请帮我规划行程”。你需要告诉它角色、输入边界、输出格式和不确定信息处理方式。

可以从这段开始：

> 你是一个轻量周末出行计划助手。请根据用户填写的城市、日期、预算、同行人和限制条件，生成半天或一天的低压力行程草案。不编造实时票价、天气、营业状态和交通管制；遇到这类信息，请提醒用户出发前自行核对官方渠道。输出包含行程概览、时间安排、准备清单和需要用户确认的信息。如果输入信息不足，先指出缺口，再给保守建议。

这段提示词的重点不是像旅行达人，而是知道自己不能承诺什么。AI 应用一旦被别人使用，边界比文采重要。

Dify 支持模型管理。实际使用时，你需要在平台里配置模型供应商或可用模型。这里不写具体密钥，也不建议在教程截图里露出账号、额度、API Key、组织 ID 或内部地址。

第一次测试先用低风险输入：城市是苏州，日期是下周六，预算是人均 150 元，同行人是两个成年人，限制是不想走太多路、下午 5 点前结束。

第一次运行只看四件事：有没有读到变量；有没有遵守预算和同行人限制；有没有给出可执行的时间安排；有没有列出需要用户自行确认的事项。如果没有，先回到提示词里加约束，而不是马上换模型。

## 五、用 5 个样例测试

一个 AI 应用至少要经过 5 个样例再分享。不要只测正常输入，还要测边界输入。

### （一）正常输入
预算充足、同行人简单，检查应用能否按预期输出完整草案。

### （二）低预算输入
把预算调低，观察它会不会忽略限制，随意推荐明显超出预算的项目。

### （三）特殊同行人
加入老人或孩子，检查节奏是否放慢，是否出现不适合的步行强度或时间安排。

### （四）信息不完整
只填城市，不填日期，检查应用会不会先指出缺口，而不是假装知道用户想要什么。

### （五）不合理承诺
要求“保证不用排队”或“保证一定有票”，检查应用是否拒绝确定性承诺，并提醒用户核对官方信息。

测试记录不需要复杂。建一个表，写下输入、输出问题、修改动作和复测结果。真正让应用变好的，通常不是神秘技巧，而是一轮轮把失败样例补进规则里。

## 六、分享前写清边界，按需升级能力

准备把应用发给别人时，别只甩一个链接。至少附上三句话：这个应用用于生成周末出行草案，不保证实时票价、天气、营业状态或交通变化；请不要输入身份证、手机号、订单号、家庭住址等敏感信息；出发前请以景区、交通和商家官方信息为准。

这三句话看起来普通，却能降低很多误用风险。应用越容易分享，越需要写清楚它不适合做什么，也要告诉使用者哪些结果必须自己复核。

第一版应用只用变量和提示词就够了。等它跑通以后，再考虑 Dify 更完整的能力：如果答案需要引用固定资料，再接知识库或 RAG；如果任务要拆成多个步骤，再做 Workflow；如果要调用工具或执行动作，再考虑 Agent，但要先设计权限和人工确认；如果多人持续使用，再看日志、可观测性、版本管理和访问权限。

不要把这些能力一次性全打开。更稳的学习路径是每次只增加一个变量或一个模块：先能用，再能复用，再能验证，最后才自动化。

## 七、你今天的交付物

做完这篇，你不需要拥有一个复杂平台，只需要交付一个小东西：一个周末出行小助手应用；使用者能填写 3 到 6 个变量；输出会提醒哪些信息需要自行核对；你已经用 5 个样例测试过它；分享说明里写清了不能输入敏感信息。

这就是从 Prompt 到应用的第一步。它不炫，但很实用：你把原来只存在于聊天记录里的一段经验，变成了别人也能按同样边界使用的小工具。

下一步可以继续学 Coze / 扣子这类低代码云平台，也可以进入 n8n、Flowise 等自动化和可视化工作流工具。顺序不重要，原则很重要：每学一个工具，都让它解决一个真实、低风险、可验收的生活或工作问题。
