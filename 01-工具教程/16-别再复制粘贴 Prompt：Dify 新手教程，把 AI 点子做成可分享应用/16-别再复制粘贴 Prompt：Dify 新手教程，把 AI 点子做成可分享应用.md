16. 别再复制粘贴 Prompt：Dify 新手教程，把 AI 点子做成可分享应用

你有没有遇到过这种时刻：你把一段 Prompt 发给同事，自己跑出来的结果明明很不错，对方却只回了一句——“第一格填什么？”

接下来你开始补说明、发示例、改格式。对方终于跑通了，下一次又来问：“预算写总价还是人均？”“这个天气是实时的吗？”一段原本想省时间的 Prompt，最后变成了一个需要你亲自陪跑的小客服。

这不是 Prompt 写得不够长，而是它还只存在于你的脑子里。Dify 的价值，就是把这些隐含的上下文，整理成别人也能看懂、愿意试一次、出了问题知道找哪里的 AI 应用。

这篇不带你逛一遍所有菜单。我们只做一个小得刚刚好的例子：周末旅行计划。用户填写出发地、目的地、日期、预算和偏好，应用生成一份有结构的行程；实时价格、天气、营业时间和预订，仍然交给人来确认。你会看到，一个“能用”的 AI 应用，真正难的从来不是把按钮点亮，而是让第一次使用的人少走弯路。


读完这篇，你不需要先学完 Dify 的所有菜单。你只需要带走一个结果：做出一个能预览、能测试、能撤回的最小应用，并知道什么时候不该继续堆功能。

这张图先记住就好：输入要说清楚，输出要有边界，结果要经过测试，分享要有人真实打开，改坏了还要能退回。后面的每一步，都是在把这五件事落地。

## 先判断：这件事值得做成应用吗？

不是所有 Prompt 都需要搬进 Dify。

如果你只是偶尔问一次问题，每次上下文都不一样，继续保存在笔记里，反而最省心。只有当同类需求反复出现、结果需要保持同一种格式，或者你准备把它交给同事、客户和社群读者使用时，做成一个小应用才真正有意义。

你可以用三个问题快速判断：

- 用户是否需要重复填写一组固定信息？
- 结果是否需要遵循相对稳定的结构？
- 你是否希望别人不用先读懂 Prompt，就能直接开始？

三个问题里有两个回答“是”，就值得试试。

拿旅行计划来说，“帮我规划一下”对你可能很自然，对第一次使用的人却不够。有人带孩子，有人预算有限，有人一天只想走几个地方。输入没说清楚，模型只能替用户猜；输出没说清楚，拿到的每份计划也很难比较。

所以别先写一段气势很足的万能 Prompt，先写下三句话：用户要提供什么、应用会交付什么、哪些事绝不能替用户拍板。这三句话，比多写几百字角色设定更能决定应用是否好用。

## 第一个应用，别追求“全能”，先让一条路径顺起来

周末旅行计划适合拿来练手，是因为它既有明确输入，也能让结果立刻变得可见。打开当前 Dify 工作区后，先按“填一次、生成一次”的单轮文本生成思路搭建。摘要、改写、提纲、计划，都可以用这条路开始。

如果你需要连续追问，再考虑 Chatbot；如果任务包含多个步骤、条件分支、知识检索或工具调用，再往 Workflow / Chatflow 走。不同部署方式、版本和套餐的页面名称可能不同，不必为了寻找旧教程里的同名按钮停下来。你只需要确认：当前形态能接收变量、能在发布前测试、能看清访问权限和版本状态。


实际操作路线很短：新建应用 → 选择 Text Generator（单轮文本生成）→ 添加变量 → 粘贴 Prompt → Preview 预览 → 通过测试后再考虑发布。不同部署和版本的按钮名称可能不同，但这条判断顺序不会变：先让一条输入到输出的路径跑通，再增加功能。

## 让用户少猜一次，应用就少失败一次

旅行计划可以先准备五个输入：出发地、目的地、出行日期、预算和偏好。输入框的提示要像一个在旁边提醒你的朋友，而不是一句模糊的“请详细描述”。

- **出发地**：从哪里出发；
- **目的地**：想去哪里；
- **日期**：哪几天出行；
- **预算**：人均还是总预算，暂时不确定也可以明说；
- **偏好**：亲子、拍照、轻松、少走路等，不确定可以留空。

然后把 Prompt 写成一份短工作约定，而不是一篇自我介绍：

```text
你是一名旅行计划助手。
请根据用户提供的出发地、目的地、日期、预算和偏好，输出：
1. 行程概览；
2. 每日安排；
3. 预算提醒；
4. 需要用户进一步确认的事项。

如果缺少关键条件，请先指出缺口；
不要擅自编造实时价格、天气、营业时间或预订结果。
```

这段 Prompt 最重要的不是把自己写得像专家，而是告诉应用：什么时候可以继续，什么时候应该停下来问一句。一个会说“不确定”的应用，往往比一个每次都给出完整答案的应用更值得分享。


可以直接用一组故意不完整的输入跑一次：

```text
出发地：上海
目的地：杭州
日期：下个月周末，具体日期未定
预算：人均 800 元
偏好：少走路，想吃本地菜
```

你应该看到的不是一份“看起来很完整”的行程，而是四个可检查结果：行程概览、每日安排、预算提醒，以及需要你进一步确认的事实。若应用直接编造具体票价或营业时间，先回到 Prompt 的边界，而不是继续加装饰。

## 第一次生成成功，不代表它真的能交给别人

预览里出现一份漂亮行程，只能证明它“有反应”，还不能证明它“适合使用”。请故意把它用错几次：

1. **信息完整**：看输出有没有稳定的骨架；
2. **缺少日期或预算**：看它会不会提醒，而不是直接猜；
3. **预算很低但要求很多**：看它会不会说清楚取舍；
4. **要求实时票价、天气或直接预订**：看它会不会明确需要人工确认。

每类留一条真实结果就够了。不要只写“看起来还行”，把问题归因到具体位置：是输入提示不清楚，Prompt 没有限制，还是模型本来就拿不到实时信息？下一次修改才会有方向。

如果你发现自己每次都在手动补同一句规则，就把规则放回应用；如果只是偶发情况，就不要让 Prompt 越写越长。

## 发布前，找一个不懂 Prompt 的人替你走一遍

真正的分享测试，不是你在管理员页面里点开预览，而是找一个没有看过内部配置的人，直接从用户视角走一遍。

你只需要请他完成三件事：填一次、读一次、指出一次不明白的地方。你重点观察：他是否知道每个输入框该填什么，能否分清“建议”和“需要确认的事实”，有没有误以为应用掌握实时信息，以及访问权限和分享范围是否符合预期。

![Dify 发布与版本迭代验收清单（原创信息图）](<assets/figures/16-别再复制粘贴 Prompt：Dify 新手教程，把 AI 点子做成可分享应用-正文插图02.png>)

发布不是“拿到链接”就结束。你还要知道对外开放的是哪个版本，改坏后能不能切回，必要时能不能先撤掉入口。图里的验收项看起来琐碎，却正是应用从“我自己会用”走向“别人也敢用”的分水岭。

## 真正值得留下的，不是菜单，而是这五条规则

当这个小应用稳定完成一次任务后，顺手留下五份轻量记录：

- **输入约定**：有哪些变量，哪些必填，缺失时怎么处理；
- **输出约定**：固定结构是什么，哪些内容不能假装知道；
- **测试样例**：正常、缺失、冲突、越界各留一条；
- **访问决定**：谁能用，哪些资料不能输入；
- **变更记录**：改了什么、为什么改、出了问题回到哪里。

以后想接知识库、工具调用或多步骤流程，先问一句：这项新能力会改变哪条输入、输出、测试或访问约定？如果说不清楚，先别急着加。

你今天不必做出一个“像产品”的大应用。只要能让另一个人不用追着你问三遍，就完成一次可理解、可检查、可回退的任务，这个小应用就已经比那段只在你电脑里有效的 Prompt 更有价值。

旅行计划只是练习。涉及实时价格、天气、支付、预约、医疗、法律、投资或安全判断时，必须接入可核验的数据源，并保留人工确认，不要让单轮文本生成替代真正的决策。
