16. 别再复制粘贴 Prompt：Dify 新手教程，把 AI 点子做成可分享应用

你可能有过这样的经历：自己写的 Prompt 用起来很顺，换个人就开始“跑偏”。对方不知道该填什么，模型也不知道哪些信息不能猜，最后你只好继续补充说明、手动改结果、再把一大段 Prompt 发回去。

这正是 Dify 值得尝试的地方。它不是把一段 Prompt 换个地方保存，而是帮你把一次性的灵感，整理成别人也能看懂、能试用、出了问题知道怎么收回的小应用。

这篇不做“大而全”的 AI 平台导览，只陪你做一个小得刚刚好的例子：周末旅行计划。用户填出发地、目的地、日期、预算和偏好，应用生成一份计划；实时票价、天气、营业时间和预订，全部留给人来确认。先把这条小路走通，你会更容易看懂后面的工作流、知识库和 Agent 到底该什么时候上场。

如果这段 Prompt 只给你自己偶尔用，放在笔记里完全没问题。只有当同类需求反复出现、结果需要比较、还要交给别人使用时，把它做成应用才值得。

先记住这五个目标：用户填得明白，结果看得懂，反例测得出，分享前有人实际打开，改坏后能退回去。

## 第一部分｜先别急着搭：你到底是在做 Prompt，还是在做一个小服务？

Prompt 负责帮你完成一次生成；应用负责把“你脑子里的上下文”交给另一个人。两者没有高下之分，区别只在于使用场景：

| 如果是这种情况 | 更适合怎么做 |
| --- | --- |
| 只是偶尔问一次，每次问题都不一样 | 继续用 Prompt，省下维护成本 |
| 同类问题会反复出现 | 把固定信息做成输入项 |
| 结果要有统一格式，方便复核 | 在 Prompt 里写清输出结构 |
| 要给同事、客户或社群读者使用 | 给用户一条不用猜的填写路径 |
| 改动后还要知道有没有变差 | 留下几条真实测试样例 |

拿旅行计划来说，用户并不只会问“帮我规划一下”。有人带孩子，有人预算有限，有人只想要轻松路线。输入没说清楚，模型只能替你猜；输出没说清楚，拿到的每一份计划也很难比较。

所以第一步不是写一段更长的万能 Prompt，而是先写三句话：

- 我需要用户提供哪些信息；
- 我会给出什么样的结果；
- 哪些事情我不会替用户拍板。

### 选择应用形态：先看任务，不要背菜单

这篇示范按 **Text Generator（单轮文本生成）** 的思路来做：填一次信息，生成一次结果。它适合摘要、改写、提纲、计划这类“一问一答”的场景。

如果你需要连续追问，可以看 Chatbot；如果任务里有多个步骤、条件分支、知识检索或工具调用，再考虑 Workflow / Chatflow。Dify 的页面名称会随部署方式、版本和套餐变化，别为了找一个旧教程里的按钮卡住。你只要确认三件事：能不能接收变量、能不能在发布前测试、能不能看清分享权限和当前版本。

## 第二部分｜从一个输入框开始：先让第一次使用的人不迷路

打开当前工作区后，先别想着把所有功能都点一遍。我们只做一条最小路径：用户填完信息，应用给出一份结构清楚的旅行计划。

可以先准备这些变量：

| 变量 | 给用户的提示 | 没填时怎么办 |
| --- | --- | --- |
| 出发地 | 从哪里出发 | 提醒补充 |
| 目的地 | 想去哪里 | 提醒补充 |
| 出行日期 | 哪几天出行 | 提醒补充 |
| 预算 | 人均或总预算 | 允许填写“未确定” |
| 偏好 | 亲子、拍照、轻松、少走路等 | 允许留空 |

这里有一个很容易被忽略的细节：输入框里的提示，不是装饰。它在替用户做决定——告诉对方填什么、填到什么程度、哪些内容可以不填。让一个第一次使用的人看一眼就知道怎么开始，比再加十条“请认真描述”更有用。

Prompt 也别写成一篇宣言。把它写成一份短短的工作约定：

```text
你是一名旅行计划助手。
请根据用户提供的出发地、目的地、日期、预算和偏好，输出：
1. 行程概览；
2. 每日安排；
3. 预算提醒；
4. 需要用户进一步确认的事项。

如果缺少关键条件，请先指出缺口，不要擅自编造实时价格、天气、营业时间或预订结果。
```

这段话的重点不是“像不像专家”，而是告诉应用什么时候该回答，什么时候应该停下来问一句。

## 第三部分｜别用一次成功骗自己：用四类输入试一遍

第一次预览能生成结果，只能证明它“有反应”，不能证明它“适合交给别人”。至少准备四类测试：

1. **正常输入**：信息完整，检查结果是否有完整骨架；
2. **缺失输入**：少填日期或预算，检查它会不会提醒，而不是直接猜；
3. **冲突输入**：预算很低但要求很多，检查它会不会说明取舍；
4. **越界输入**：要求它给出实时票价或直接预订，检查它是否明确需要人工确认。

每类留下一条真实结果就够了。不要只记“看起来还行”，把不满意的地方写下来：是问题出在输入提示、Prompt 约束，还是模型本身无法获得实时信息？这样下一轮修改才有方向。

如果你发现自己每次都在手动补同一条规则，就把规则放回应用里；如果只是一种偶发情况，就别急着把 Prompt 越写越长。

## 第四部分｜发布前，找一个不懂 Prompt 的人试一次

真正的分享测试，不是你在管理员页面里点开预览，而是找一个没有看过内部配置的人，直接从用户视角走一遍。

让对方只做三件事：填一次表单、读一次结果、告诉你哪里不明白。你重点观察：

- 他是否知道每个输入框该填什么；
- 他是否能看懂结果里哪些是建议、哪些需要确认；
- 他是否误以为应用掌握实时信息；
- 访问权限、登录要求和分享范围是否符合你的预期。

Dify 不同版本、部署方式和工作区的发布入口可能不完全一样。不要把“拿到链接”当成发布完成。你还需要知道：当前对外的是哪个版本，改坏后能不能切回，必要时能不能先撤掉入口。

## 第五部分｜把这五样东西留下，应用才不会越改越乱

当这个小应用能稳定完成一次任务后，顺手留下五份轻量记录：

- **输入约定**：变量、必填规则和缺失时的处理方式；
- **输出约定**：固定结构、不能假装知道的内容；
- **测试样例**：正常、缺失、冲突、越界各一条；
- **访问决定**：谁能用，哪些资料不能输入；
- **变更记录**：改了什么、为什么改、出问题退回哪里。

以后想接知识库、工具调用或多步骤流程，先问一句：这项新能力会改变哪条输入、输出、测试或访问约定？说不清楚，就先不要加。

## 最后：一个能被别人顺利用起来的小应用，比一段“看起来很聪明”的 Prompt 更有价值

如果你今天只完成了输入设计和四类测试，也已经足够。Dify 的价值不在于让你把功能菜单全部点亮，而在于让一个小想法从“我自己会用”，变成“别人也能按同一条路径用”。

旅行计划只是练习。涉及实时价格、天气、支付、预约、医疗、法律、投资或安全判断时，必须接入可核验的数据源，并保留人工确认，不要让单轮文本生成替代真正的决策。
