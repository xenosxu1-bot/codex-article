**16. 别再复制粘贴 Prompt：Dify 新手教程，把 AI 点子做成可分享应用**

很多人做 AI 工具，第一步不是打开开发平台，而是把同一段 Prompt 复制到不同聊天框里：这次改语气，下次补格式，过几天连自己都找不到“最好用”的那一版。问题不在 Prompt 不够长，而在它没有变成一个别人能稳定使用的入口。

这篇只做一个周末级别的小项目：把“根据几项信息生成旅行计划”做成一个低风险、可重复运行、可以分享给朋友测试的应用。第一次上手走云端路线，先把输入、输出、测试和分享闭环跑通；自托管、模型服务和团队权限放到后面。

你不需要先学会工作流编排，也不用一开始就接知识库。先做出一个只解决一个问题的小工具，看看它是否真的比复制粘贴省事。

## 一、先把场景收窄，再决定应用要做什么

先不要写“万能旅行助手”。把任务写成一句能验收的话：

> 用户填写出发地、目的地、日期、预算和偏好，应用输出一份按天排列的旅行建议，并明确哪些内容需要用户自行确认。

这句话已经包含了输入、输出和边界。它不承诺实时交通、实时价格，也不替用户做安全或财务决定。第一次练习最好避开医疗、法律、投资、招聘、账号操作和其他高风险场景。

再列三件“不做的事”：不自动预订，不保证价格实时，不替用户确认景点是否营业。边界越早写清，后面越不容易把一个小工具吹成“智能管家”。

## 二、用云端路线完成第一个应用

Dify 提供云端使用和自托管等路线。新手第一次验证想法，优先使用当前可访问的云端入口；只有在数据、网络、部署或团队管理确实需要时，再评估自托管。不同版本、套餐和工作区权限可能影响页面和功能名称，以下步骤按当前界面寻找对应入口即可。

先完成最小配置：进入应用创建入口，选择适合文本输入输出的应用类型，给它起一个能说明用途的名字，例如“周末旅行计划”。创建后，不要马上添加知识库、工具调用和多分支工作流；先确认空应用能打开编辑页。

如果页面要求配置模型，先选择当前工作区可用的模型提供商和模型。模型列表、额度和权限由账号、套餐及服务状态决定，不要把某个账户看到的选项写成所有人都能使用的固定菜单。

官方入口：

- [Dify 官方文档](https://docs.dify.ai/)
- [Dify GitHub 仓库](https://github.com/langgenius/dify)

### 中文页面怎么找，不被按钮名称卡住

如果你打开的是中文界面，不要把教程当成“逐字翻译菜单”。不同版本、工作区权限和云端/自托管路线，按钮名称可能不完全相同；按下面这条路径找功能更稳：

1. **先找中文入口**：从 [Dify 中文官网](https://dify.ai/zh) 进入官方文档或工作区，优先看官方资料，不把第三方教程当成唯一依据。
2. **再找创建应用**：在工作区寻找“创建应用”、`Create App` 或“应用编排”入口，第一次只做一个输入少、输出清楚的小应用。
3. **接着找输入配置**：在开始节点、用户输入或变量配置区域，建立出发地、目的地、日期等字段，并写清必填与空值处理。
4. **然后找预览调试**：用正常输入、缺少必填项、越界要求和相对日期各跑一次；不要只用一条成功样例。
5. **最后找发布入口**：在“发布”、`Publish` 或 `Web App` 附近找到分享地址；复制链接只是拿到地址，必须再用非作者身份打开并完成一次输入测试。

## 三、把 Prompt 拆成读者看得懂的变量

不要让用户在一个大文本框里重新描述全部需求。把需要变化的内容拆出来，用户才知道该填什么，应用也更容易测试。

| 变量 | 示例 | 是否必填 | 空值处理 |
| --- | --- | --- | --- |
| 出发地 | 深圳 | 是 | 未填写时提示补充 |
| 目的地 | 厦门 | 是 | 未填写时不生成计划 |
| 日期 | 2026-08-22 | 是 | 要求使用 YYYY-MM-DD |
| 预算 | 每人 1500 元 | 否 | 未填写时只给路线建议 |
| 偏好 | 亲子、少走路 | 否 | 未填写时使用中性建议 |

变量名可以调整，但输入规则要写在字段说明里。日期不要让用户只写“下周六”，因为相对日期会随阅读时间变化；教程示例中的 2026-08-22 仅用于测试，真实使用时让用户填写具体日期。

如果某个变量必须存在，就在提示词中明确处理空值。不要指望模型自动理解“没填预算”意味着“预算不限”，这两种情况会直接影响输出。

## 四、写提示词，完成第一次运行

在提示词里只保留完成任务所需的规则，不要用十几段口号堆出“专业感”。可以先用这个版本：

> 你是一名旅行计划整理助手。请根据用户填写的出发地、目的地、日期、预算和偏好，输出一份简洁的行程建议。
>
> 先列出你采用的已知条件；再按天给出安排，每天包含地点、活动建议和交通提醒；最后单独列出需要用户自行核对的内容，例如营业时间、票价、天气、交通班次和安全要求。
>
> 如果关键信息缺失，先提出最多三个补充问题，不要自行编造。不要声称已经查询实时价格、已经完成预订或已经确认景点开放。

运行一次后，不要只看文字是否顺眼。检查它有没有使用变量、有没有漏掉日期和预算、有没有把“不确定”说成确定事实。

## 五、用五类输入做一次可记录的测试

测试不能只用一条“深圳去厦门怎么玩”。至少准备五类输入，并把结果记进表格：

| 测试类型 | 输入 | 预期结果 | 不通过时怎么修 |
| --- | --- | --- | --- |
| 正常输入 | 信息完整、偏好明确 | 按天输出，条件没有丢失 | 检查变量是否正确插入 |
| 缺少必填项 | 不填目的地 | 先追问，不直接生成 | 补充必填规则和空值处理 |
| 缺少选填项 | 不填预算 | 仍能给通用建议 | 明确默认行为 |
| 越界要求 | 要求实时价格或自动预订 | 说明无法确认，不冒充已完成 | 加入能力边界 |
| 口语日期 | “下周六出发” | 要求具体日期 | 加入日期格式提示 |

测试时保留一条失败样例。它比一张漂亮的成功截图更能说明应用有没有被真正验收。修改 Prompt 后，至少重新跑一次正常输入和一次边界输入，避免修好一个问题又破坏另一个问题。

## 六、发布 Web App，并验证分享边界

标题写了“可分享应用”，正文就必须走完分享这一步。完成测试后，在当前界面找到应用的发布、Publish 或 Web App 入口，先发布一个测试版本，再用另一种浏览器或未登录状态打开访问地址。

你要验证四件事：

1. 访问者能否打开应用，而不是只能看到编辑页面。
2. 访问者是否只需要填写输入，不会接触你的工作区设置、模型密钥或内部资料。
3. 应用是否会暴露不该公开的 Prompt、知识库内容、调试信息或个人数据。
4. 修改 Prompt 后，已分享地址使用的是旧版本还是新版本；如果不再使用，能否撤销或关闭访问。

![Dify 新手发布前验收清单](<assets/figures/16-别再复制粘贴 Prompt：Dify 新手教程，把 AI 点子做成可分享应用-正文插图02.png>)]

别把“复制链接成功”当成发布完成。真正的发布验收是：一个不参与制作的人，能从链接打开、按说明填写、得到可读结果，而且没有越过你设定的权限边界。

如果页面提供公开访问、登录访问、密码或其他权限选项，按实际风险选择，不要为了方便默认公开。涉及内部资料、客户信息或未公开工作流时，先停用分享，改用受控账号测试。

## 七、先留下一个可复用的小工具，再考虑升级

Dify 的价值不在于你一次性打开了多少节点，而在于一个重复问题终于有了固定入口。完成第一次闭环后，留下三样东西：一份变量说明、一组通过与失败样例、一条发布前检查清单。

后续再考虑接知识库、工具调用、工作流分支或自托管。每加一个能力，都重新检查数据来源、模型权限、失败处理、费用和许可证边界。开源仓库的许可证和云端服务条款也可能更新，团队或商业用途不要只看一篇旧教程。
