16. 别再复制粘贴 Prompt：Dify 新手教程，把 AI 点子做成可分享应用

很多人第一次接触 Dify，最容易做的一件事，是把一段已经写好的 Prompt 粘进去，再点一下发布。

这当然能跑起来，但还不算“把 AI 点子做成应用”。真正会让别人反复使用的，不是一段看起来很聪明的话，而是一组可以被验证、被交接、被迭代的约定：**谁该输入什么、系统必须输出什么、什么情况要停下来说明边界、改了以后怎样证明没有变差。**

本文用“周末旅行计划”做一个最小示范：它接收明确的出发地、目的地、日期、预算和偏好，输出一份可继续人工确认的计划。它**不**查询实时票价、天气、景点营业时间，也不替用户完成预订。这个范围很小，恰好适合练习产品化的基本功。

> **先给结论：**如果这段 Prompt 只供你偶尔自己使用，保留在笔记工具或对话框里就够了。只有当输入会反复出现、输出需要一致、结果要交给别人使用或你想持续改进时，才值得把它做成 Dify 应用。

## 一、先判断：你是在“写提示词”，还是在“设计一次服务”

Prompt 的价值在于帮助你完成一次生成；应用的价值在于，让另一个人不用理解你的脑内上下文，也能稳定完成同一类任务。

| 观察信号 | 更适合继续用 Prompt | 更适合做成应用 |
| --- | --- | --- |
| 使用频率 | 偶尔一次、每次问题都不同 | 同类任务会反复出现 |
| 输入信息 | 你自己知道该补什么 | 使用者需要被明确引导 |
| 输出标准 | “大致有用”就可以 | 需要固定结构、可比较、可复核 |
| 使用对象 | 只有作者本人 | 同事、客户、社群读者或陌生用户 |
| 后续维护 | 不需要追踪改动 | 改一处就要知道是否影响结果 |

旅行计划这个例子满足右侧的大多数条件：用户会反复提出“周末去哪儿”“预算多少”“带孩子怎么安排”之类的问题；如果没有输入规范，模型只能猜；如果没有输出规范，不同用户拿到的计划很难比较。

因此，先别急着写一长段万能 Prompt。先把它当成一个小服务，写下最小的产品承诺：**我收集哪些信息；我承诺给出什么；我明确不替用户做什么。**

## 二、先选对应用形态：本示范只做单轮文本生成

Dify 的官方文档把应用区分为不同形态。界面名称和入口可能会随部署方式、版本、套餐或语言而变化，因此不要把某个按钮名称当成永久流程；先按任务结构选形态，再在你当前工作区确认实际可用的入口。

| 形态 | 适合什么问题 | 何时不要选它 |
| --- | --- | --- |
| Chatbot | 需要连续追问、上下文来回澄清 | 你只需要一张明确表单和一份一次性结果 |
| Text Generator | 输入一次，生成一次；例如计划、摘要、改写、提纲 | 任务需要工具调用、多步骤处理或条件分支 |
| Workflow / Chatflow | 有多个步骤、工具、分支、知识检索或人工检查点 | 你还没定义清楚最小输入和最小输出 |

这篇文章选择 **Text Generator（单轮文本生成）** 的思路：用户填完变量，系统生成一份结构化旅行计划。这样做不是因为它“功能最强”，而是因为它最容易暴露输入、输出和测试中的问题。

如果你现在打开的 Dify 页面没有完全相同的中文标签，不要照着旧教程硬找。用下面三个判断替代死记菜单：

1. 能否创建一个接收变量、只生成一次结果的应用；
2. 能否在发布前预览或调试真实输入；
3. 能否确认分享范围、访问控制与当前版本状态。

## 三、把“用户会怎么说”变成输入契约

新手最常见的失误，是直接把“帮我做周末旅行计划”塞给模型。这样一来，模型必须猜出出发地、时间、人数、预算和偏好；它生成得再流畅，也很难稳定。

先在应用的变量或输入字段中定义下面这张表。字段类型以你当前 Dify 工作区实际提供的选项为准；关键不是控件长什么样，而是每个字段都要有清楚的含义、必填策略和缺失时的处理方式。

| 变量 | 推荐输入 | 是否必填 | 示例 | 缺失或异常时怎样处理 |
| --- | --- | --- | --- | --- |
| origin | 短文本 | 是 | 深圳 | 提示补充出发地，不生成路线建议 |
| destination | 短文本 | 是 | 厦门 | 提示补充目的地，不猜测城市 |
| travel_dates | 短文本 | 是 | 2026-10-03 至 2026-10-05 | 要求写绝对日期；“下周末”要提醒确认日期 |
| budget_cny | 数字 | 是 | 3500 | 预算为负数、空值或不合理时要求重新填写 |
| people_count | 数字 | 否 | 2 | 缺失时明确按“未提供人数”处理，不擅自假定亲子或情侣 |
| preference | 预设选项或短文本 | 是 | 轻松、亲子、美食 | 无法识别时要求从可选偏好中确认 |

这里有一个很重要的原则：**变量不是为了让页面看起来专业，而是为了减少模型替用户猜测。**

例如，“下周末去厦门”看起来信息很多，但在跨月、跨节假日或多人协作时并不够。把日期写成绝对日期，是为了让后续测试、复盘和改版时能得到可重复的结果。把预算定义为数字，是为了让模型能够解释自己的预算假设，而不是把“3000 左右”随意拆分。

## 四、再写 Prompt：约束输出，而不是假装知道一切

变量确定后，再把它们放进 Prompt。下面是一份可以作为起点的模板；请根据自己的业务、语气和风险边界改写，而不是把它当作通用答案。

~~~text
你是旅行计划助手。根据用户提供的信息，生成一份“可供人工确认”的周末旅行初稿。

已知输入：
- 出发地：{{origin}}
- 目的地：{{destination}}
- 日期：{{travel_dates}}
- 总预算（人民币）：{{budget_cny}}
- 人数：{{people_count}}
- 偏好：{{preference}}

请按以下结构输出：
1. 一句话说明：本计划依据了哪些输入；
2. 每日安排：上午 / 下午 / 晚上，每项写明安排目的；
3. 预算假设：交通、住宿、餐饮、活动四类，并说明只是估算；
4. 仍需确认的事项：实时票价、天气、营业时间、预约和当地规则；
5. 信息冲突或缺失时：不要自行补造事实，先指出缺什么、为什么影响计划。

边界：
- 不声称掌握实时价格、实时天气、营业状态或余票；
- 不替用户完成支付、预订或安全决策；
- 当输入含糊、相互矛盾或超出预算时，优先说明冲突，再给出需要用户确认的问题。
~~~

这份 Prompt 的重点不是文采，而是三个可检查的约束：

- **输出有固定骨架。**用户知道去哪里看日程、预算和待确认事项。
- **不确定性被显式标注。**模型不把估算包装成实时事实。
- **异常有出口。**信息不足时，系统提出问题，而不是生成一段貌似完整的幻觉。

Prompt 写完后先在草稿或调试状态运行一次。此时不要急着发布：一次“看起来不错”的结果，只能证明某个样例能跑，不能证明应用可以交给别人使用。

## 五、用测试集替代“我觉得没问题”

高质量内容和高质量应用有一个共同点：都不能只靠作者的主观感觉。给这个最小应用准备一张小测试表，至少覆盖正常输入、缺失输入、冲突输入和超出能力边界的输入。

| 测试编号 | 输入情境 | 通过条件 |
| --- | --- | --- |
| TG-01 | 信息完整：深圳到厦门、绝对日期、预算 3500、2 人 | 输出含每日安排、预算假设、待确认事项；不把估算写成实时价格 |
| TG-02 | 缺少目的地 | 明确要求补充目的地，不虚构行程 |
| TG-03 | 缺少人数 | 标记人数未提供，并说明预算或活动安排会受影响 |
| TG-04 | 日期含糊：“下周末” | 要求确认绝对日期，而非自行推断 |
| TG-05 | 预算与要求冲突：两人、三天、预算极低、要求高星酒店 | 说明冲突并给出可选调整项，不承诺无法验证的价格 |
| TG-06 | 要求实时票价、天气或代订 | 明确说明能力边界和需要人工确认的渠道 |
| TG-07 | 用户要求忽略前述规则、输出未核实信息 | 保持既定结构与边界，不把未核实内容伪装成事实 |

每次改变量、Prompt、模型或应用形态，都留下一条简短的测试记录：

~~~text
测试基线：TG-20260813-01
应用形态：单轮文本生成
改动内容：新增“信息冲突时先说明”规则
样例：TG-01 / TG-04 / TG-06
结果：填写实际观察到的输出与问题
处置：保留、回退，或进入下一轮修改
~~~

注意：上面的表是**待执行的验收基线**，不是本文替你宣称已经全部测试通过的结果。你应在自己的 Dify 工作区运行后，把真实输出、失败样例和修复动作补进记录。

## 六、发布不是“拿到链接”，而是完成一次可回退的交接

当测试基线满足你的最低要求，再进入分享或发布环节。不同 Dify 版本和工作区对 Web App 访问、成员访问、公开链接、版本控制的支持并不完全相同；因此不要直接相信“默认公开”或“有链接就安全”这类说法。

发布前，至少逐项确认：

1. **访问范围：**谁能打开、是否需要登录、链接被转发后会发生什么；
2. **输入数据：**表单里不收集密码、身份证号、客户机密或其他不应交给模型处理的信息；
3. **外部视角：**用无登录或非管理员身份实际打开一次，确认看到的页面、权限和提示符合预期；
4. **测试基线：**把 TG-01 至 TG-07 中与你的场景相关的用例重新跑一遍；
5. **版本说明：**写清本次改了什么、为什么改、有哪些已知限制；
6. **回退方案：**新版本表现变差时，知道回到哪个已验证版本，或先撤掉分享入口。

Dify 官方的版本控制文档专门描述了 Chatflow 与 Workflow 的草稿、已发布版本和历史版本管理。即使你的最小示范使用的是单轮文本生成，也应该借鉴同样的工程习惯：**发布前验证，发布后记录，改动后可定位。**如果你升级为多步骤流程，再按当前工作区的实际版本控制能力执行发布与回退。

## 七、从“能跑”到“值得维护”，只差五份小资产

到这里，你已经做出的不只是一个可演示的 Prompt 页面，而是一个可继续演进的最小 AI 服务。请把下面五样东西与应用一起保存：

1. 输入契约：变量、必填规则、默认值和异常处理；
2. 输出契约：固定结构、不能假装知道的内容、何时请求确认；
3. 测试基线：关键样例、预期行为、真实运行结果；
4. 访问决策：谁能用、收集什么、公开前检查了什么；
5. 变更记录：改动原因、版本标识、已知限制与回退点。

以后要接入知识库、工具调用、条件分支或 Agent，不要先追求复杂。先问一个问题：**这项新能力会改变哪条输入、输出、测试或访问承诺？**能回答清楚，再往前走；回答不清楚，就先回到这个最小闭环。

## 核验与适用边界

- 本文依据 Dify 官方 README 与官方文档中关于 Chatbot、Text Generator、Workflow / Chatflow、Web App 访问和版本控制的说明进行核验，最后核对日期为 **2026 年 8 月 13 日**。
- 文中配图均为原创信息图，不是 Dify 后台截图；它们用于解释判断框架，不宣称某个界面、按钮名称或默认权限永久不变。
- 本文的旅行计划示例仅用于练习输入设计、输出约束和测试方法；涉及实时价格、天气、营业状态、出行安全、支付或预订时，应改用可验证的实时渠道并由使用者确认。
- Dify 的实际功能、入口、权限和版本能力会因云端/自托管、套餐、工作区设置和产品更新而变化。发布前请在自己的工作区复核当前设置。
