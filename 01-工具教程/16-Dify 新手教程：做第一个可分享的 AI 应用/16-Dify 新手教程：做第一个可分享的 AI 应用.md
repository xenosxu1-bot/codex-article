**16. Dify 新手教程：做第一个可分享的 AI 应用**

你可能已经有过这样的经历：某个 Prompt 写得很好，能帮你改周报、整理旅行计划、生成客服回复。可一旦同事、家人或朋友也想用，你就只能复制一大段文字给他，然后不断解释这里改成你的城市、这里填预算、这里别乱删。

这时，你需要的不是再写一版更长的 Prompt，而是把它做成一个可以填写、可以测试、可以分享的小应用。

前两篇我们完成了两件事：第 14 篇让本地 AI 助手跑起来，第 15 篇把散落资料变成可问答知识库。今天继续往前：用 Dify 做第一个可分享的 AI 应用。

> 资料核验时间：2026-08-11。Dify 的产品定位、Docker Compose 快速启动、工作流、RAG、Agent、模型管理、可观测性和许可证边界，以 Dify 官方 GitHub README、官方文档入口和 LICENSE 为准。本文配图为本仓库原创信息图，不使用官方 Logo、官网截图或第三方博客图片。

## Dify 不是更漂亮的聊天框

Dify 官方把自己定位为开源 LLM 应用开发平台。它把 AI Workflow、RAG pipeline、Agent 能力、模型管理和可观测性放在一个平台里。对新手来说，先不要被这些词吓到，你只需要抓住一个最小闭环：输入变量、提示词、模型、输出结果、分享或复用。

普通聊天里，你每次都要重新解释背景。Dify 的价值，是把那些固定背景和可变信息分开：固定部分写进应用配置，可变部分让使用者填写。

比如周末出行小助手。固定部分是：你希望 AI 给出轻松、不赶路、适合家庭的行程；可变部分是：城市、日期、预算、同行人、不能接受的安排。

这就是应用化的开始。

## 先选一个窄问题，不要上来做万能助手

第一款应用一定要小。越小，越容易测试；越容易测试，越不容易把错当成功。

我建议用这个练手场景：周末出行小助手。输入城市、出行日期、预算、同行人、忌口或限制；输出半天或一天的轻量行程，并列出需要用户自行确认的信息。

它适合新手，因为风险较低，又能马上验证。你不需要接真实订单，不需要处理支付，也不需要承诺天气、票价、营业时间永远准确。你只要把 AI 定位成计划草案助手，并提醒用户出发前核对官方信息。

不要第一天就做这些应用：投资建议、用药判断、合同审核、简历筛选、自动发邮件、自动下单。它们不是不能做，而是需要更严格的事实、权限、日志和人工审核。

## 云端体验还是本地自托管

Dify 可以使用官方云服务，也可以自托管。官方 README 当前提供了 Docker Compose 快速启动路径：进入仓库的 docker 目录，复制 .env.example 为 .env，再执行 docker compose up -d，随后通过本机安装入口初始化。

如果你是纯新手，我建议这样选：

| 你的目标 | 建议 | 原因 |
| --- | --- | --- |
| 只想理解应用怎么搭 | 先用云端或现成环境体验 | 少被部署问题打断，先学变量和测试 |
| 想学习自托管 | 按官方 Docker Compose 文档走 | 能理解模型、数据库、服务和配置之间的关系 |
| 团队或商业部署 | 先读 LICENSE 和部署文档 | 多租户、前端版权、Logo 和数据边界不能凭印象处理 |

无论哪条路线，都不要把真实密钥、客户资料、内部文档直接拿来练手。模型供应商、日志、应用分享链接和团队权限都会影响数据边界。

## 第一步：把 Prompt 拆成变量

很多 Prompt 失败，不是写得不够长，而是把所有信息混在一段话里。Dify 应用化的第一步，是把用户每次都会变的内容拆出来。

以周末出行小助手为例，可以设计五个输入：

| 变量 | 用户填写示例 | 用途 |
| --- | --- | --- |
| city | 杭州 | 限定城市范围 |
| date | 本周六 | 提醒用户核对天气、营业时间和交通 |
| budget | 人均 200 元 | 控制建议档次 |
| people | 两个大人一个小学孩子 | 决定节奏和体力强度 |
| constraints | 不想排队太久，孩子晕车 | 排除不适合安排 |

变量不要太多。第一版 3 到 6 个就够了。每多一个输入，使用者就多一分放弃的可能。

## 第二步：写一段有边界的系统提示词

应用提示词不要只写请帮我规划行程。你需要告诉它角色、输入边界、输出格式和不确定信息处理方式。

可以从这段开始：你是一个轻量周末出行计划助手。请根据用户填写的城市、日期、预算、同行人和限制条件，生成半天或一天的低压力行程草案。不编造实时票价、天气、营业状态和交通管制；遇到这类信息，请提醒用户出发前自行核对官方渠道。输出包含行程概览、时间安排、准备清单和需要用户确认的信息。如果输入信息不足，先指出缺口，再给保守建议。

这段提示词的重点不是像旅行达人，而是知道自己不能承诺什么。AI 应用一旦被别人使用，边界比文采重要。

## 第三步：接入模型，但别把密钥写进文章或截图

Dify 支持模型管理。实际使用时，你需要在平台里配置模型供应商或可用模型。这里不写具体密钥，也不建议在教程截图里露出账号、额度、API Key、组织 ID 或内部地址。

第一次测试时，先用低风险输入：城市是苏州，日期是下周六，预算是人均 150 元，同行人是两个成年人，限制是不想走太多路、下午 5 点前结束。

看输出时不要只问像不像人写的。你要检查四件事：有没有把实时信息说成确定事实；有没有忽略预算和同行人限制；有没有给出可执行的时间安排；有没有列出需要用户自行确认的事项。

如果没有，就回到提示词里加约束，而不是马上换模型。

## 第四步：做 5 个测试样例

一个 AI 应用至少要经过 5 个样例再分享。不要只测正常输入，还要测边界输入。

样例 1：预算充足，同行人简单。样例 2：预算很低，看看它会不会乱推荐高消费项目。样例 3：带老人或孩子，看看节奏是否放慢。样例 4：用户只填城市，不填日期，看看它是否提醒信息不足。样例 5：用户提出不合理要求，比如保证不用排队，看看它是否纠正承诺。

测试记录不需要复杂。建一个表，写下输入、输出问题、修改动作和复测结果。你会发现，真正让应用变好的不是神秘技巧，而是一轮轮把失败样例补进规则里。

## 第五步：分享前写清楚使用说明

当你准备把应用发给别人时，别只甩一个链接。至少附上三句话：这个应用用于生成周末出行草案，不保证实时票价、天气、营业状态或交通变化；请不要输入身份证、手机号、订单号、家庭住址等敏感信息；出发前请以景区、交通和商家官方信息为准。

这三句话看起来普通，却能降低很多误用风险。AI 应用越容易分享，越需要写清楚它不适合做什么。

## 什么时候需要知识库或工作流

第一版应用只用变量和提示词就够了。等你跑通以后，再考虑 Dify 更完整的能力：如果答案需要引用固定资料，再接知识库或 RAG；如果任务要拆成多个步骤，再做 Workflow；如果要调用工具或执行动作，再考虑 Agent，但要先设计权限和人工确认；如果多人持续使用，再看日志、可观测性、版本管理和访问权限。

不要把这些能力一次性全打开。新手最好的学习路径，是每次只增加一个变量：先能用，再能复用，再能验证，最后才自动化。

## 你今天的交付物

做完这篇，你不需要拥有一个复杂平台，只需要交付一个小东西：一个周末出行小助手应用；使用者能填写 3 到 6 个变量；输出会提醒哪些信息需要自行核对；你已经用 5 个样例测试过它；分享说明里写清了不能输入敏感信息。

这就是从 Prompt 到应用的第一步。它不炫，但很实用：你把原来只存在于聊天记录里的一段经验，变成了别人也能按同样边界使用的小工具。

下一步可以继续学 Coze / 扣子这类低代码云平台，也可以进入 n8n、Flowise 等自动化和可视化工作流工具。顺序不重要，原则很重要：每学一个工具，都让它解决一个真实、低风险、可验收的生活或工作问题。
